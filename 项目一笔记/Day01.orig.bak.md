开发依赖(project.optional-dependencies):开发(包括但不限于修改这个项目功能,复刻这个项目),测试、调试、检查、构建这个项目时才用的工具，部署到生产环境可以不装。
运行依赖:**项目跑起来、提供服务时必须装的依赖。**
- **前端**：负责展示和交互（浏览器、手机 App）
- **后端**：负责处理和计算（你的 RAG 逻辑 + FastAPI）
**FastAPI**定义的是负责的是接收到前端的请求之后该怎么交给后端处理(怎么调用后端服务得到结果)
因为前端（网页、App、或者你测试用的工具）不能直接伸手进你的 Python 代码里调用函数，它必须通过一个**约定的入口**发请求。FastAPI 就是这个入口(它可以将后端的服务包装成HTTP接口给前端用)
**uvicorn**:是 `FastAPI` 的“**黄金搭档**”, 是一个高性能的 **ASGI 服务器**,负责监听网络端口、接收 HTTP 请求，然后把请求转交给 `FastAPI` 去处理，最后再把处理结果返回给用户
为什么要它:
因为**FastAPI**不会自己去监听 8000 端口，不会自己接收 TCP 连接，不会自己解析 HTTP 原始字节，也不会自己把响应写回网络(就是不会处理网络方面的东西),这些是服务器干的活,所以这些活就要交给**uvicorn**,让它来处理这些,之后将处理好的结果交给FastAPI,和将结果**包装成符合 HTTP 协议的响应**要求传给前端
**pydantic**:是用来提供给FastAPI调用的一个检验数据的工具,当FastAPI接收到uvicorn解析出来的数据之后,如果定义了**pydantic**,它就会先去检验这个数据符不符合我们的要求,如果不符合我们的要求,会告诉FastAPI,之后FastAPI返回422错误
**python-multipart**:因为FastAPI只能看的懂普通的请求(Json),倘若是文件或者其他看不懂的他就会调用python-multipart来将这些东西转换成FastAPI能看得懂的东西
**Qdrant**：一个用 Rust 编写的高性能**向量搜索引擎**（或叫向量数据库），它负责真正地存储和计算。
**qdrant-client**：一个 Python 库，它**不是**数据库本身，而是你用来**指挥** Qdrant 干活的工具。它提供了一套 Python 接口，让你不用去拼原始的 HTTP 请求，就能完成所有操作
这就是经典的**客户端-服务器架构**。Qdrant 是服务器，`qdrant-client` 是你手里的遥控器
`qdrant-client` 主要负责三件事，正好对应 RAG 流程中“检索”这部分的**核心操作**：
1. **创建“仓库”（集合）**：在 Qdrant 里，数据是按“集合”（Collection）来组织的，你可以把它理解成一张表。`qdrant-client` 可以帮你创建一个集合，并定义好向量的维度（比如 384 或 768 维）和相似度度量方式（比如余弦相似度）。[](https://mintlify.wiki/qdrant/qdrant/api/clients/python#next-steps)
2. **“存入”向量（Upsert）**：当你把文档切块并向量化之后，`qdrant-client` 负责把这些向量，连同它们的原始文本、来源等元数据（Payload），一起“上传”并存入 Qdrant 的集合中。[](https://mintlify.wiki/qdrant/qdrant/api/clients/python#next-steps)
3. **“搜索”相似向量（Search）**：当用户提问时，你把问题也向量化，然后用 `qdrant-client` 去 Qdrant 里搜索，它会快速返回最相似的几个向量（Top-K）以及它们对应的原始文本片段。
**sentence-transformers:** 是负责**把“文本”变成“向量"** 的 Python 库。没有它，Qdrant 里就没有东西可存，检索也无从谈起,它用到的核心技术是**预训练的 Embedding 模型**
**Dockerfile 是把项目和运行环境打包成镜像(集装箱)的说明书，目的是:以后不管搬到哪台电脑，打开镜像就能直接跑**
它按顺序：选基础环境 → 设参数 → 装系统工具 → 装运行依赖 → 复制代码 → 声明端口 → 设健康检查 → 设启动命令
**docker-compose.yml是“多集装箱编排说明书”**——你之前学的 `Dockerfile` 是“怎么打包一个集装箱”，而 `docker-compose.yml` 是“**要几个集装箱,每个集装箱怎么造,怎么把几个集装箱一起开起来，并且让它们互相能说话**”
**Dockerfile：“一个集装箱的建造图纸”**
它只回答一个问题：**“这一个集装箱里面装什么、怎么装、启动时跑什么命令**
**docker-compose.yml：“整个店的运营计划书”**
它回答的是：**“店里要开几个集装箱？每个集装箱用图纸造还是买现成的？它们怎么连？谁先启动？端口怎么开？数据存哪？**
注意:如果有两个集装箱要自己造,但是**造法却不同**,**那就需要两份 Dockerfile**
但是它们的位置不是随便放的,而是有固定的组织方式的:
最常见的组织方式:
项目根目录/
├── api/
│   ├── Dockerfile        ← api 的图纸
│   └── ...代码
├── worker/
│   ├── Dockerfile        ← worker 的图纸
│   └── ...代码
└── docker-compose.yml
